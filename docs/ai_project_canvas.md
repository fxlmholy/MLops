# AI Project Canvas — Bakery Daily Demand Prediction (P1 / M1)

| องค์ประกอบ | รายละเอียด |
|---|---|
| **Value Proposition** | เจ้าของร้านรู้ล่วงหน้าว่าพรุ่งนี้ควรเตรียมสินค้าแต่ละชนิดเท่าไร → ลดของขาดและของเหลือทิ้ง |
| **Customer / User** | เจ้าของร้าน, พนักงานฝ่ายผลิต (คนอบขนมตอนเช้า) |
| **Prediction Task** | Regression (quantile) — ยอดขายรายสินค้าของวันถัดไป |
| **Decision** | จำนวนที่ควรเตรียม = ceil(F_q) − ของคงเหลือ, q = (ราคา − ต้นทุน)/ราคา |
| **Data Sources** | French Bakery Daily Sales (Kaggle), ปฏิทินวันหยุด |
| **Data Collection / Labels** | label = ยอดขายจริงของวันนั้น (ได้มาฟรีจาก POS ทุกวัน) |
| **Features** | lag 1/7/14, rolling mean/std, วันในสัปดาห์, เดือน, วันหยุด, สินค้า |
| **Offline Metrics** | WAPE, MAE, Pinball loss @ q |
| **Business Metrics** | stockout rate, waste rate, กำไรที่หายไป/วัน |
| **Gating** | ดีกว่า seasonal-naive ≥ 10%, p95 < 200 ms, model < 50 MB |
| **Making Predictions** | Batch ทุกคืน + Real-time API |
| **Live Monitoring** | PSI (data drift), rolling WAPE (concept drift), latency/error |
| **Risks / ผลกระทบเมื่อผิด** | ทำนายต่ำ → ของหมด เสียลูกค้า; ทำนายสูง → ของเหลือทิ้ง ขาดทุน |
| **Cost / Feasibility** | ข้อมูลฟรี (POS ของร้าน / Kaggle) · โมเดล LightGBM เทรนบน CPU ได้ภายในไม่กี่นาที ไม่ต้องใช้ GPU · รันบนเครื่องเดียวด้วย Docker compose · ต้นทุนหลักคือเวลาทีมดูแล pipeline และ monitoring · คุ้มค่าเมื่อของเหลือทิ้ง/ของขาดลดลงมากกว่าค่าดูแลระบบ |

## 5 คำถามตรวจสอบหัวข้อ
1. **ทำนายผิดใครเดือดร้อน:**
   - ทำนาย **ต่ำ** เกินจริง → เตรียมของไม่พอ ของหมดก่อนปิดร้าน → เสียยอดขายและลูกค้าไม่พอใจ (เจ้าของร้าน + ลูกค้า)
   - ทำนาย **สูง** เกินจริง → อบเกิน ขนมปังสดขายข้ามวันไม่ได้ → ของเหลือทิ้ง ขาดทุนค่าวัตถุดิบ (เจ้าของร้าน + ฝ่ายผลิต)
   - ความเสียหายสองฝั่งไม่เท่ากัน → จึงใช้ quantile forecast (p_q) แทนค่าเฉลี่ย และเลือก q จากราคา/ต้นทุน (newsvendor)
2. **ตัวชี้วัดธุรกิจ ↔ ตัวชี้วัดโมเดล:**
   - ธุรกิจ: stockout rate (วันที่ของหมด), waste rate (สัดส่วนของเหลือ), lost profit/วัน
   - โมเดล: **WAPE** (ความผิดพลาดรวมเทียบยอดขายรวม อ่านง่ายสำหรับเจ้าของร้าน และไม่พังเมื่อยอดบางวัน = 0 ซึ่ง MAPE พัง) + **Pinball loss @ q** (วัดคุณภาพ quantile ที่ใช้ตัดสินใจจริง)
   - ความเชื่อม: pinball loss @ q ต่ำ ⇒ จำนวนที่เตรียมใกล้จุดสมดุลระหว่างของขาดกับของเหลือ ⇒ lost profit ต่ำ → ตรวจสอบโดย simulate บน test set
3. **Data / Concept Drift ที่คาดว่าจะเกิด:**
   - **Data drift (P(X) เปลี่ยน):** ฤดูกาลท่องเที่ยว/วันหยุดยาว ทำให้ยอดและสัดส่วนสินค้าเปลี่ยน, เพิ่ม/ยกเลิกเมนู, ร้านเปลี่ยนเวลาเปิด-ปิด → ตรวจด้วย PSI > 0.2
   - **Concept drift (P(y|X) เปลี่ยน):** คู่แข่งเปิดใกล้ร้าน, ขึ้นราคา, เทรนด์สุขภาพ → feature เหมือนเดิมแต่ยอดจริงเปลี่ยน → ตรวจด้วย WAPE 7 วันล่าสุด > 1.2 × WAPE ตอน deploy
4. **ต้องตอบเร็วแค่ไหน / ปริมาณคำขอ:**
   - งานหลักเป็น **batch**: พยากรณ์ทุกสินค้าตอนกลางคืน ต้องเสร็จ **ก่อน 06:00** ก่อนเริ่มอบ
   - **Real-time API** สำหรับถามรายสินค้า/ปรับจำนวนระหว่างวัน: ร้านเดียวมีคำขอน้อย (หลักสิบ/วัน) แต่ตั้ง SLO p95 < 200 ms, error < 1%, availability ≥ 99% เพื่อรองรับการขยายหลายสาขาและให้ใช้งานลื่น
5. **โมเดลใหม่แย่กว่าเดิม รู้ได้อย่างไร / ย้อนกลับอย่างไร:**
   - **ก่อน deploy:** gate อัตโนมัติ — ต้องชนะ seasonal-naive ≥ 10% (WAPE), ชนะ champion ปัจจุบัน, ผ่าน schema, model < 50 MB, p95 < 200 ms → ไม่ผ่าน = reject ไม่ promote
   - **หลัง deploy:** monitor rolling WAPE 7 วัน + PSI + latency/error ถ้าเกินเกณฑ์ → alert
   - **ย้อนกลับ:** MLflow Model Registry ย้าย alias `champion` กลับเวอร์ชันก่อน (`make rollback`) แล้ว API reload โมเดล — ไม่ต้อง build/deploy ใหม่

## ทำไมใช้ ML แทน rule
- **Rule ที่ใช้เทียบ (baseline):** seasonal-naive — "พรุ่งนี้ขายเท่าวันเดียวกันของสัปดาห์ก่อน" ซึ่งคือวิธีที่ร้านส่วนใหญ่ใช้อยู่แล้ว
- **ข้อจำกัดของ rule:** ไม่รู้จักวันหยุด/เทศกาล, ไวต่อวันผิดปกติวันเดียว (เช่น สัปดาห์ก่อนฝนตก ยอดตก → สัปดาห์นี้เตรียมน้อยตาม), ให้ค่าเดียวไม่มีช่วงความไม่แน่นอน จึงตัดสินใจแบบ newsvendor ไม่ได้
- **ML ทำได้มากกว่า:** รวมหลายสัญญาณ (lag หลายช่วง, ค่าเฉลี่ยเคลื่อนที่, วันในสัปดาห์, วันหยุดฝรั่งเศส, ชนิดสินค้า) และทำนาย quantile ได้โดยตรง
- **เงื่อนไขการยอมรับ:** ML ต้องชนะ seasonal-naive ด้วย WAPE ดีกว่า **≥ 10%** บน test set (ช่วงเวลาหลังสุด) — ถ้าไม่ชนะ ให้ใช้ rule ต่อ เพราะง่ายกว่าและดูแลถูกกว่า
